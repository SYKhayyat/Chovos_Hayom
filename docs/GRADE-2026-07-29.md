## 2. Attacking the instrument first

Before trusting any reading, I broke things on purpose to confirm the suite goes red.

**Mutation test — 5 mutations, 5 killed.** Each mutation was applied to `lib/`, the full suite run,
then reverted:

| Mutation | Result |
|---|---|
| `RollUp` drops the out-of-range clamp (`learned` may exceed `total`) | **KILLED** |
| `BackupValidator` skips the parent-cycle check | **KILLED** |
| `FoldLog` clears the learned-date on a *partial* un-mark | **KILLED** |
| `importInto` ignores `replace` (never deletes stale events) | **KILLED** |
| Event validation drops the negative-duration check | **KILLED** |

This is a genuinely good result and it is worth saying plainly: **these assertions can fail.** No
"deletes the line then asserts the line is gone" pattern was found. There is no `|| true`, no
swallowed failure, one `catch` in the whole test tree (and it is in the double's transaction
rollback, where it belongs, and it rethrows).

**CI gate test — verified red-able.** I deleted `settingsClearTitle` from `app_he.arb` and ran
`flutter gen-l10n`. `l10n_untranslated.json` correctly became `{"he": ["settingsClearTitle"]}`,
which the CI step fails on. Restored; back to `{}`. The translation gate is real, not decorative.

**Where the instrument does fail.** `test/support/in_memory_progress_repository.dart` carries this
docstring:

> *"It is still a faithful implementation rather than a stub ... because a test double that is
> easier to satisfy than the real repository proves nothing about the real repository."*

It is faithful on transactions (real snapshot-and-restore) and on stream emission. It is **not**
faithful on constraints: it stores events in `Map<profileId, List<LearningEvent>>` and therefore
has no global uniqueness on event id, while the real table's primary key is `{id}` alone. That is
precisely the divergence that hid F1 — and since `DriftProgressRepository` has no test at all, the
divergence had nowhere to be caught.

## 3. Findings

### F1 — Importing one backup into a second profile crashes (High)

**Reproduction** (`test/grader/event_id_collision_test.dart`, red):

```
SqliteException(1555): while executing statement, UNIQUE constraint failed:
learning_events.id, constraint failed (code 1555)
  drift_progress_repository.dart 42:15  DriftProgressRepository.addEvents
  backup_service.dart 212:19           BackupService.importInto
```

- `lib/data/drift/database.dart:48` — `LearningEvents.primaryKey => {id}`, profile-blind.
- `lib/application/backup_service.dart:196` — `importInto` de-duplicates against
  `_repo.getEvents(targetProfileId)`, i.e. **only the target profile's** ids.
- `lib/data/repositories/drift_progress_repository.dart:42` — `addEvents` is a bare `insertAll`
  with no conflict clause.

So every event id in the backup is "new" to profile 2 while already present in the table under
profile 1, and the insert dies. The import is inside a transaction, so nothing is corrupted — it
fails cleanly — but a documented feature (profiles + import; moving progress to a family member's
profile on the same device) does not work at all.

**Family.** I enumerated all six tables from the schema rather than trusting the pattern.
`CustomNodes`, `CustomLayers`, `RequiredLayerConfigs` and `OfferedLayerConfigs` **all** key on
`{profileId, ...}`. `LearningEvents` is the sole outlier. The fix already exists in the codebase —
`database.dart:127` carries the comment:

> *"Custom nodes are profile-scoped: two profiles may hold nodes with the same id (e.g. the same
> backup imported into both). The primary key must include profileId, or the second import throws
> a uniqueness violation."*

That is a verbatim description of F1, written about a different table, applied there and never
generalised. This is the highest-value defect found precisely because the diagnosis was already
in the repo.

### F2 — The Hebrew dashboard renders its progress numbers backwards (Medium-High)

**Reproduction** (`test/grader/bidi_numerals_test.dart`, red). Laying out `'5 / 100  (5%)'` under
`TextDirection.rtl` and measuring the glyph boxes:

```
first logical character "5" -> x = 168.0
last  logical character ")" -> x =   0.0
```

The line is fully reversed. A Hebrew reader sees `(5%)  100 / 5`.

Nothing in `lib/` uses a bidi isolate (`Bidi`, U+200F, U+2068) — a grep finds only chevron flips
and two `textDirection:` overrides on text fields — so the Unicode bidi algorithm resolves the
neutrals itself: digits are weak-LTR, and `/`, `(`, `%` surrounded by spaces are neutral.

Affected, confirmed by usage grep:
- `progressCount` = `'{learned} / {total}  ({percent}%)'` → `features/dashboard/progress_tile.dart:223`
  — **every row of the tree**, the most-seen number in the app.
- `statsLearnedValue` = `'{learned} / {total}'` → `features/stats/stats_screen.dart:71`.

**Measured, not assumed:** `meforishCoverage` = `'{learned}/{total}'` is **safe**. A slash directly
between two digits is a Common Separator and joins the numeric run, so it stays left-to-right. Only
the space-padded forms break. My initial hypothesis would have wrongly flagged it; the probe
corrected me.

`rtl_layout_test.dart` asserts chevron direction and tree indent as geometry — good tests — but
lays out no string, so the suite has no opinion on this. `fixes.md`'s own "Still open" section
names *"numbers inside RTL sentences"* as an untested risk. The suspicion was right; this is the
measurement, and it lands on the headline number rather than an incidental one.

### F3 — The calculator freezes the UI for ~3 seconds, per keystroke (Medium)

**Reproduction** (`test/grader/predictor_cost_test.dart`, red): `Predictor.finishDateWithCycle`
with `remaining: 2711, amounts: [0.0001]` takes **2,988 ms** before returning `null`.

`CalculatorScreen._compute` (`calculator_screen.dart:196`) runs synchronously inside `build()`,
reading straight off the `TextEditingController`s, and every field is wired
`onChanged: (_) => setState(() {})` (lines 139, 147, 158, 168). The only guard is `daily <= 0`.
Any positive amount too small to finish inside the 200,000-day cap walks the entire loop, one
`DateTime.add` allocation per iteration, on the UI thread, on every keystroke.

Reachability, computed from the real catalog:
- whole Torah (12,092 units): any amount below **0.0605/day**
- Shas alone (2,711 units): any amount below **0.0136/day**

So `0.05` typed into the daily field freezes the app for three seconds — and again on the next
keystroke. `finishDateWithShabbos` has the same shape with a 50,000 cap (~750ms).

The repo already budgets latency elsewhere (`test/domain/derive_cost_test.dart`), so the discipline
exists; this path simply has no budget on it.

### F4 — "Restore" does not undo everything it says it undoes (Medium)

**Reproduction** (`test/grader/restore_scope_test.dart`, red): export a backup, create a custom
sefer afterwards, restore the backup with `replace: true` — the custom sefer is still there.

The UI promises, twice:

> `settingsRestoreFileSubtitle`: *"Make this profile exactly match a backup, undoing anything recorded since it"*
> `restoreConfirmIntro`: *"This makes the profile exactly match the backup, undoing everything recorded since it."*

`importInto`'s own doc comment is narrower and **accurate** — *"the profile's **log** is made to
match the backup exactly"* — and only the log is reconciled. `addCustomNode`,
`addCustomLayer`, `setLayerRequirement` and `setOfferedLayers` all upsert; a row the backup does
not contain is never removed. So custom sefarim, custom mefarshim and every required/offered layer
config created since the backup survive a restore that promised to undo them.

The gap is between the implementation (correctly scoped, correctly documented) and the user-facing
copy (over-promising). Either the copy narrows to "your learning history", or the restore extends
to the rest of the profile.

### F5 — The restore preview can predict the wrong numbers (Low, **by inspection — not reproduced**)

`_restoreDiff` (`settings_screen.dart:427`) computes the preview using
`ref.read(layerRequirementsProvider)` — the *current* required-layer sets. `importInto` then
overwrites those sets from the backup. So when a backup carries different requirements, the
"N units will no longer be marked" warning, and the identical numbers reused afterwards as the
report, are computed against a requirement set that the restore itself is about to replace.

The comment above it claims *"the prediction and the outcome are the same numbers"*. That holds only
when the backup's requirements match the current ones. I did not build the fixture to reproduce
this; it is reasoned from the code and flagged as such.

- **The app running.** I built the Windows release binary but did not launch it. Nothing here is a
  statement about how it behaves on screen.
- **Hebrew idiom.** Machine-complete and enforced, but grammatical ≠ idiomatic. Needs a native
  reader. (`fixes.md` already says this.)
- **Screen readers.** `grid_semantics_test.dart` asserts labels exist; no real TalkBack/Narrator run.
- **Crash-mid-write.** No SIGKILL-during-transaction test. Drift/SQLite gives real atomicity, so
  this is lower risk than the LiNix analogue, but it is untested.
- **Real `file_picker` behaviour** per platform — the desktop-vs-mobile write asymmetry at
  `settings_screen.dart:459` is reasoned about carefully in comments and exercised by nothing.
- **Long-history performance on real hardware.** `derive_cost_test.dart` budgets the fold as a unit
  test; no measurement on a phone with years of events.

## 5. Grades by area

The bar applied: **A = verified working under adversarial testing; B = correct as far as it is
tested, with real gaps; C = works on the happy path; D = untested where it matters; F = broken.**

| Area | Grade | Why | To move up one letter |
|---|---|---|---|
| Domain / correctness core | **A** | 95–97% covered; 5/5 mutations killed; the `learned > total` clamp genuinely holds; the one-pass fold is careful and its partial-un-mark semantics are exactly right | property/fuzz testing of the fold against a reference model |
| Schema & migrations | **A−** | idempotent, replay-safe, ordered deliberately (the "additive before rebuild" rule), tested against real on-disk SQLite — the one bug class that bricks an app permanently is taken seriously | a test that kills the process mid-migration and re-opens |
| Persistence layer | **D** | 0/198 lines. One confirmed crash (F1) in a documented feature, found within minutes of pointing a test at it | any test suite at all against `DriftProgressRepository` — F1 dies immediately |
| Test infrastructure | **B+** | assertions genuinely fail when they should; CI gates verified red-able; no un-failable checks found | make the double enforce the real table's constraints, and run the backup suite against both |
| Data safety / destructive paths | **B−** | restore computes a real diff, confirms in units, colours the button red — this is better than most apps ship | make the copy match the scope (F4) |
| Localization & RTL | **C+** | string table complete and *enforced*; layout mirroring done as geometry — but the headline number reads backwards in Hebrew (F2) | bidi-isolate the numeric templates, and assert glyph order in the RTL test |
| UI / interaction layer | **D+** | 20% on `unit_grid`; the primary logging flows are 0% | widget tests for the five sheets |
| Performance | **B−** | one-pass derive with an explicit cost budget is real discipline | put a budget on `_compute` and stop running it in `build()` (F3) |
| Documentation & honesty | **A−** | unusually honest; comments explain *why*, name past bugs, and pre-flag the RTL numeral risk that turned out to be real | fix the two places the copy over-promises (F4, and the double's docstring) |

## 6. Verdict

This is a well-engineered application with a serious and specific blind spot.

The core is the real thing. The append-only-log-with-everything-derived decision is correct and
carried through honestly: `learned > total` is structurally impossible, the fold's partial-un-mark
semantics are subtler than most people would bother getting right, migrations are replay-safe with
a stated ordering rule, and the analyzer config is genuinely strict rather than decorative. The
comments explain reasoning rather than restating code, and repeatedly name bugs the author already
made. Five deliberate mutations to core invariants were all caught. That is not a codebase coasting
on green checkmarks.

What a user can rely on: the arithmetic. Marking, rolling up, folding, predicting, and the schema
surviving an upgrade.

What they cannot: importing a backup into a second profile — it fails outright. Reading their own
progress percentage in Hebrew — it renders reversed on every row of the dashboard. Typing a small
number into the calculator without a three-second freeze. And "Restore from file" doing what its
own confirmation dialog says it does.

The pattern connecting all four: **this project tests what it can reason about and does not test
what it has to touch.** Pure functions are at 95%; SQLite and the widget tree are at 0–20%. All
four defects live on that line. The suite is not weak — it is correctly built and pointed at the
wrong half of the app. The most valuable next commit is not a fix; it is the first test file that
instantiates `DriftProgressRepository`, because F1 was sitting one `expect` behind that door.

**Overall: B.** Would be an A− with the persistence layer under test and the two user-visible
defects (F1, F2) closed.

## 2. Attacking my own instruments first

Doctrine §2 says audit the instrument before trusting its readings, and rule 7 says an assertion
against a system in the wrong state fails *toward false positives*. Both earned their keep. I record
this section because it is the most transferable part of the round.

**Three oracles that measured nothing.** Each looked authoritative and was worthless:

| Oracle | Why it was silent | Verdict |
|---|---|---|
| `logcat \| grep "Skipped N frames"` | `Choreographer` watches the Android **main** thread; Dart runs on Flutter's own UI thread | dead |
| `dumpsys gfxinfo <pkg>` | reported `Total frames rendered: 0` — Flutter does not render through HWUI | dead |
| whole-screen pixel diff after a keystroke | `TextEditingController` repaints `EditableText` on its own, **before** the parent's `setState` runs the expensive compute — so the character appearing looked like the answer arriving | misleading |

Only the fourth attempt — hashing **just the prediction band**, with a cheap-input control run to
measure the probe's own cost, then amplifying to ten keystrokes — produced a number I trust. Had I
stopped at oracle 1 or 2, I would have reported "no jank found" and been wrong; had I stopped at
oracle 3, I would have reported ~500 ms and been wrong the other way.

**Four findings I nearly filed and killed instead:**

1. *"The log sheet's text fields expose no accessibility label."* My dump parser read `text` and
   `content-desc` but not `hint`. Both fields carry proper hints. **My bug.**
2. *"The desktop window opens 226×32 pixels at −25600,−25600."* `IsIconic` was true — a minimized
   window's rect, and −25600 is −32000 scaled by 125 % DPI. **My bug.**
3. *"On Windows the app lays out wider than its window and clips the right edge of every row."* I had
   screenshots that looked damning. My PowerShell host was DPI-**unaware**, so `GetWindowRect`
   reported 1280×720 for a real 1600×900 window and `CopyFromScreen` captured its top-left corner.
   One `SetProcessDpiAwarenessContext` call and the app rendered perfectly. **My bug** — and the one
   I came closest to filing, because the evidence was vivid.
4. *"The backup reminder overcounts: 14 units unsaved, 1 unit learned."* `BackupReminder.evaluate`
   dedupes distinct units *touched* since the export, deliberately including un-marks, and says so
   in a comment. My own mark/un-mark probing had touched exactly the extra units. **Correct by
   design.**

**Two observations I cannot explain and am not filing.** Honesty demands they appear somewhere:
the dashboard tree once dumped as fully expanded ~30 s after a screenshot showed it collapsed, and
did not reproduce in three deliberate attempts; and my first bulk-undo attempt left the action
undone and the history still showing "1 undoable action", while a carefully re-sequenced second
attempt reported "Undone — 156 events removed" and persisted across a force-stop. Both involved
multi-second gaps between my injected taps. I attribute both to my driving rather than to the app,
with less confidence than I would like.

### F1 — cross-profile import — **still reproduces, and is worse than reported** (High)

The test-level exception is unchanged. What hardware added is what the *user* sees. Export from
"Default", create profile "Yosef", Settings → Import from file, choose that file:

> **Import failed: the file could not be read.**  `[Details]`

The in-app crash log holds the real cause:

```
--- 2026-07-30T07:28:45.284187 · Importing your backup
SqliteException(1555): while executing statement, UNIQUE constraint failed:
learning_events.id, constraint failed (code 1555)
  Causing statement: INSERT INTO "learning_events" ("id", "profile_id", …)
  parameters: 216d0460-af05-45ea-8e3f-8cd532761dd6, 4b8328c3-f4ae-4973-a79f-dc61fa733f8a,
              shabbosShas, 2, 0, 1785409705, 1785409705, null, null, null, null
```

The file was read, parsed and validated. The failure is ours — `LearningEvents.primaryKey => {id}`,
the one table of six that omits `profileId`. And the message blames the file. The app tells this
same user, twice, that the export is *"the only copy that survives losing it"*; the reasonable
response to "could not be read" is to delete it and make another, which fails identically.

Mechanism at `settings_screen.dart:442` — a `SqliteException` is not a `BackupFormatException`, so
every failure that is the app's own falls through to the branch that describes the file. This is the
laundered-failure shape from doctrine §2.2: a malformed file, an app bug, and an unreadable file
collapse into one sentence naming the only cause that is the user's fault.

The transaction rolls back cleanly — Yosef stayed at 0/12,092 — so nothing is corrupted. The feature
is simply unusable. New probe: `test/grader/import_error_wording_test.dart`.

### F2 — Hebrew numerals — **confirmed on two real screens** (Medium-High)

Yesterday measured glyph boxes in a harness. Here it is painted, on the phone and on Windows. Every
row of the tree, left to right on screen:

```
(0.0%)  929 / 0          ← the row that means "0 learned of 929"
(0.1%)  2,684 / 4        ← Shas
(0.0%)  12,092 / 4       ← Kol HaTorah Kula
```

The whole line mirrors, so the operands swap: `0 / 929` paints as `929 / 0`. Sentence-level order is
right for an RTL reader (the numerator is encountered first, rightmost); the *fraction* is not — a
numeric expression is conventionally left-to-right even in Hebrew, which is why the fix is a bidi
isolate rather than a reordering. The app already disagrees with itself here: `meforishCoverage`
(`{learned}/{total}`, no spaces) stays `4/12,092` because an unspaced slash joins the numeric run,
which yesterday's probe pinned as the safe case. Same fact, two renderings, one app.

Unchanged in `lib/l10n/app_he.arb:55` and `:295`. Confirmed identically on Windows, so it is not a
platform font artifact.

### F3 — calculator cost — **mechanism confirmed, severity overstated** (Low, was Medium)

This is a correction, and it is mine to make: yesterday's "freezes the UI for ~3 seconds, per
keystroke" was measured in the **`flutter test` JIT VM**, not in a release build.

On the device, AOT, worst case (`0.05`/day → the full 200,000-iteration walk in
`finishDateWithCycle`, confirmed by the resulting *"בקצב הזה לעולם לא תסיים"*), measured by
amplifying to ten expensive keystrokes and subtracting a cheap-input control:

```
CHEAP     10 keystrokes | settled 1893 ms after inject | total 2129 ms
EXPENSIVE 10 keystrokes | settled 2284 ms after inject | total 2933 ms
                                              → ~80 ms per keystroke
```

~80 ms is about five dropped frames — real jank while typing, not a freeze. The defect is still a
defect: an unbounded synchronous loop inside `build()`, with no budget on it, reachable by ordinary
input. But it does not deserve the severity the prior grade gave it, and the general lesson is
sharper than the specific one: **a latency measured under `flutter test` is not a user-facing
latency.** The repo's own `derive_cost_test.dart` budget has the same caveat.

## 4. New findings

### G1 — the primary logging action sits under the system navigation bar (High-Medium)

The app's main flow is: long-press a daf → *"Log with date / duration / note"* → fill in → **Mark
learned**. On this phone that confirm button is laid out at y = 2532…2667. The navigation bar owns
y = 2577…2712. So the bottom ~90 px of a 135 px button is not the app's.

Reproduction, and the experiment that distinguishes "looks overlapped" from "is dead":

```
$ adb shell input tap 990 2640      # inside the button's own reported bounds
$ adb shell dumpsys activity activities | grep topResumedActivity
  topResumedActivity=ActivityRecord{… com.motorola.launcher3/com.android.quickstep.RecentsActivity …}
```

Aiming at the app's primary action opened **Recents**. The visible upper strip does work (a tap at
y = 2560 saved the log), so the button is two-thirds dead rather than wholly dead — which is worse
to diagnose, because it works when you happen to hit high.

**Mechanism**, `log_unit_sheet.dart:229` and `:234`:

```dart
final bottomInset = MediaQuery.of(context).viewInsets.bottom;
padding: EdgeInsets.fromLTRB(16, 8, 16, 16 + bottomInset),
```

`viewInsets` is the keyboard. The nav bar is `viewPadding`. Nothing accounts for it — so the sheet is
correct while the keyboard is up (verified: the buttons lift to y = 1420…1555, clear of everything)
and wrong whenever it is down, which is the state it opens in.

**Family — enumerated from the code, not from the pattern.** Nine `showModalBottomSheet` call sites.
Seven wrap their content in `SafeArea`: `sort_sheet:31`, `bulk_actions_sheet:67`,
`mefarshim_config_sheet:90`, `unit_details_sheet:51`, `unit_layers_sheet:73`, `cycles_screen:80`, and
the cell menu at `unit_grid_screen:264`. The only two that do not — `log_unit_sheet:229` and
`add_chazara_sheet:79` — are **exactly** the two that reach for `viewInsets.bottom` instead. The
keyboard inset replaced the nav-bar inset rather than adding to it. Confirmed on the device for both:
"Log chazara" lands on the identical y = 2532…2667. I verified the cell menu's last item ends at
y = 2577 — flush with the nav bar, correct — which is what a properly-padded sheet looks like here.

Android 15+ enforces edge-to-edge, so this is every current phone, not an exotic setup.

Probe: `test/grader/sheet_nav_bar_inset_test.dart`. Watched it fail (button bottom 784 vs nav-bar top
752), then watched it **pass** with one line changed (`+ MediaQuery.of(context).viewPadding.bottom`),
then reverted — so the assertion is satisfiable and the fix is a one-liner in two files.

### G2 — a profile with no backup gets a green tick (Medium-Low)

A fresh profile's Settings → Backup tile:

> ✅ *(green `verified_outlined`)* **Never exported**
> Everything you have learned is in that backup

"that backup" does not exist. The green tick is the same all-clear shown to a fully-exported profile.
`settings_screen.dart:687-700` keys the title off `neverBackedUp` and the icon+subtitle off
`unsavedUnits == 0`, and never reconciles them; both-true is every profile on its first day.
`BackupReminder` is not at fault — with no events, zero unsaved units is the truth. The tile draws
the wrong conclusion from it. Verified that the neighbouring states are right: at 156 marked units the
same tile read "Never exported / 156 units learned since — they exist only on this device" with the
red shield, and after an export, "Last exported 2026-07-30 / Everything you have learned is in that
backup". Only the corner a new user occupies is wrong.

Probe: `test/grader/backup_tile_never_exported_test.dart`.

### G3 — desktop keyboard support is partial, and invisible where it exists (Medium, Windows/desktop)

Tab traversal works and app-bar actions draw a clear focus ring. In the grid, established by
experiment rather than by looking: five Tabs then Enter **marked daf 7** — so cells are focusable and
Enter activates them — yet no screenshot before the Enter shows any focus indicator on any cell. A
keyboard user marks blind. (Cells are `InkWell`s inside a filled dark `Container`; the default focus
highlight does not register against it.)

And the cell menu has no keyboard route at all. `_UnitCell` binds `onTap`, `onLongPress` and
`onSecondaryTap` — the comment at `unit_grid_screen.dart:433` says *"Right-click / secondary-tap opens
the same menu — desktop-friendly, no touchscreen required"*, which is true for a **mouse**.
Shift+F10 produced nothing. Verified from the code that nothing else could have:

```
$ grep -rn "CallbackShortcuts|Shortcuts(|Actions(|onKeyEvent|SingleActivator|LogicalKeySet" lib/
  (no matches — only three `autofocus: true` on text fields)
```

So with a keyboard alone you can toggle "learned" and nothing else: no duration, no haara, no
chazara, no *View / edit details*. Also observed: the settings list did not respond to Page Down
after clicking into it (mouse wheel scrolls it fine). Against the project's own rule that every
action work with mouse **and** keyboard, this is a real gap; mouse users are unaffected.

### G4 — the app cannot fit its own name in its title bar (Low)

English, default font, 1220 px phone: the app bar reads **"Chovos …"**. At 1.6× font scale,
**"Chovo…"**. Five actions plus the drawer button crowd it out. Hebrew ("חובות היום") fits, so this is
English-only. Cosmetic, but it is the first thing every English user sees.

### G5 — the disambiguator is baked into the data (Low)

120 of 312 catalog names carry a hard-coded parenthetical. So inside Shas you read "Moed (Shas) →
Shabbos (Shas)", where the qualifier is pure noise; while Mishnayos masechtos are bare, so a search
for "shabbos" returns four rows of which the *first* — plain "Shabbos, 24 perakim" — is the one you
cannot identify. The qualifier belongs in the search result, computed from the ancestor, not in the
node's name. (One entry is qualified by kind rather than corpus: `Taharos (Mesechta)`.)

### G6 — switching profiles switches the app's language (Low)

With Default in Hebrew, creating and switching to a second profile flipped the whole UI to English
and LTR; switching back restored Hebrew. Settings are per-profile by design, and language rides in
them. Defensible, but language, theme and calendar are device chrome rather than per-learner
preference — and a Hebrew-only user who creates a profile for their son lands in an English settings
screen to find the toggle back.

### G7 — search truncates silently (Low)

`catalog_search_delegate.dart:21` — `.take(50)` with no indication that results were dropped.
Doctrine's "no silent caps".

## 5. What hardware verified as working

Recorded because a grade that lists only defects is not a measurement. All of this was unverified
yesterday and is verified now.

- **Accessibility is genuinely good.** The tree exposes grid cells as `CheckBox` with real state —
  `'daf 2, learned, 1 chazara'` — tree rows as one sentence per row, every icon button named
  (`'Open navigation menu'`, `'Siyum calculator'`), and both text fields carrying hints. A screen
  reader has something correct to say on every surface I visited. `grid_semantics_test.dart` was
  asserting the right things.
- **Deep links.** `chovoshayom://sefer/shabbosShas` cold-starts into the right grid.
  `…/no-such-sefer` → *"This sefer no longer exists. It may have been hidden, deleted, or replaced."*
  `…/nonsense/xyz` and `…/sefer/` → *"There is nothing here. "chovoshayom://nonsense/xyz" is not a
  screen this version of the app has."* Three distinct, accurate messages that quote the URL back.
  The manifest's claim holds.
- **The Android export writes real bytes.** The `_pickerWritesTheFile` asymmetry that
  `settings_screen.dart:459` worries about ("the dialog succeeds, the guard reports 'Saved backup',
  and nothing was ever written") is correct on Android: 1,449 bytes of valid JSON in
  `/sdcard/Download/chovos_hayom_backup.json`, all five events including the chazara note, `.json`
  suffix intact, visible to the import dialog's filter, and the "last exported" stamp updated.
- **Destructive paths are well guarded.** Finish-all confirmed with *"This changes 156 units"* and
  *"You can undo it from Settings → Bulk action history for as long as you like"*; the undo then
  reported *"Undone — 156 events removed"* and survived a force-stop. Roll-up arithmetic was right at
  every step (156/12,092 = 1.3 %).
- **The crash log is an asset.** Full stack, timestamped, labelled with what the user was doing

- **RTL mirroring is correct** everywhere except the numerals: drawer from the right, actions
  reversed, grid filling right-to-left (daf 2 top-right), chevrons and badges flipped, back arrow
  becoming a forward arrow, bilingual mefarshim rows.
- **1.6× font scale** holds on both the dashboard and the grid — no clipping.
- **Windows desktop** renders correctly at 125 % scaling, reflows the grid to 18 columns at 1600 px,
  searches Hebrew nodes by Latin transliteration, and toggles cells on click.
- **Cold start 686 ms**, and 307 ms warm.

## 8. Verdict

Sixteen surfaces had never been executed by a person. Twelve of them worked the first time, several
of them impressively: the accessibility tree is correct enough for a screen reader on every screen I
visited, four malformed deep links produce four accurate sentences, R8 did not break SQLite, and the
bulk-destructive path confirms in units and then actually undoes. That is not the profile of a
codebase that has been getting by on unverified claims.

Four did not work, and the pattern is the same one yesterday's grade named — this project tests what
it can reason about and not what it has to touch — with a sharper edge on it. Three of the four
defects are things **no test could have seen and one minute on a phone shows immediately**: a confirm
button under the navigation bar, a progress fraction reading backwards in Hebrew, a green tick over a
backup that does not exist. The fourth, F1, was already known and is worse than it looked: it does
not merely fail, it tells the user their only backup is unreadable.

What a user can rely on today: the arithmetic, the schema, marking and un-marking, bulk actions and
their undo, the Android export actually writing a file, deep links, and a screen reader.

What they cannot: importing a backup into a second profile — and the error message will point them at
the wrong culprit. Reading their progress fraction in Hebrew. Hitting *Mark learned* or *Log chazara*
where the button appears to be. Trusting the green tick on a new profile. Doing anything on a desktop
beyond toggling "learned" with a keyboard alone.

I also owe a correction: yesterday's F3 said the calculator freezes for ~3 seconds per keystroke. It
was measured in the test VM. On a real phone it is ~80 ms — jank, not a freeze. The mechanism is real
and the severity was not.

**Overall: B.** It does not fall, because everything the last round could not test turned out to
work. It does not rise, because the app's primary action is two-thirds untappable on every current
Android phone, and finding that took one long-press.

The most valuable next commit is still not a fix. It is the first widget test that pumps a sheet with
a non-zero `viewPadding.bottom`, because G1 was sitting one `expect` behind that door — exactly as F1
was sitting behind the door of the first test to instantiate `DriftProgressRepository`.

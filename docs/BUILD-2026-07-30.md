## 1. The work orders

### W1 · F1 — an event id belongs to a profile, not to the database

**Red, before.** `test/grader/event_id_collision_test.dart` — `SqliteException(1555): UNIQUE
constraint failed: learning_events.id`. `LearningEvents.primaryKey` was `{id}`, the only one of six
tables that omitted `profileId`; the same backup imported into a second profile collided with
itself.

**Fix.** Schema v11 rebuilds the table with `{profileId, id}` — the change `custom_nodes` got at v2,
with a comment on that table describing this exact failure and never generalised. The migration is
guarded on the live schema and on the table existing, and re-creates the batch index afterwards
because a rebuild takes its indexes with it.

**Family, enumerated from the code rather than from the pattern.** An id that is unique only within
a profile makes every find-by-id-alone a cross-profile write. Three sites:

| site | before | after |
|---|---|---|
| `removeEvents(List<String>)` | deleted from whichever profile matched | takes the profile it acts in |
| `updateEvent` | matched `id` alone | matches both halves of the key |
| `removeEvent(String)` | profile-blind, documented "used by undo", **called by nothing** | deleted |

**Cleared with reasons:** `removeBatch` and `deleteProfile` were already profile-scoped — verified
rather than assumed, and both now carry a test saying so. `addEvents` needs no conflict clause: the
import de-duplicates against the target profile before writing.

**Watched fail.** The cross-profile hazard is only *reachable* after the key changes, so it was
written against the pre-fix API and run: `removeEvents(['shared'])` wiped Reuven's whole log
(`Bad state: No element`) and `updateEvent` edited the wrong profile's row. Both green after.

**Also found while fixing it, and it is the more dangerous half:** my v11 step called
`alterTable` on a table it had not confirmed exists. `_isPartOfPrimaryKey` answers false both for
"the key lacks this column" and for "there is no such table", and a migration that throws during
`beforeOpen` is the one failure a user cannot get out of. The v9→v10 fixture, which seeds only
`profiles`, caught it.

**Second half — what the user is told.** `importError` reported every non-format failure as "the
file could not be read", so our own constraint violation told someone their only backup was corrupt.
Three causes, three sentences now; the utf8 decode is where "could not be read" is raised, and it is
the only place that says it.

**Independent reproduction.** Export from one profile, create a second, Settings → Import from file,
choose that export. `flutter test test/data/ test/grader/event_id_collision_test.dart`

### W2 · G1 — a sheet may reach under the navigation bar; its buttons may not

**Red, before.** `sheet_nav_bar_inset_test` — the confirm button's bottom edge at 784 against a
nav-bar top of 752. On the phone this was two thirds of "Mark learned" dead, and a tap inside its
own bounds opened Recents.

**Fix.** `SafeArea` at the `showModalBottomSheet` builder for both offending sheets, matching the
shape the cell menu already used, with the keyboard inset kept inside it. The two compose:
MediaQuery's `padding` is already zero at the bottom while the keyboard covers it.

**Family.** All nine sheets, from the code: seven wrapped themselves in `SafeArea` and were never
affected; the only two that reached for `viewInsets.bottom` instead — `log_unit_sheet` and
`add_chazara_sheet` — are exactly the two that broke. `sheet_insets_test.dart` now opens **seven** of
the nine on a view with a 48px navigation bar and asserts no control that starts above the bar's top
edge ends below it. It carries a control — a sheet built the broken way, which the same assertion
must reject — because a geometry check that cannot fail is what let this ship.

**Not covered, said plainly:** the cell menu and the cycles sheet open from inside a screen rather
than from a callable function. Both wrap in `SafeArea` and the cell menu was measured flush on the
device; that is evidence, not a test.

**Reproduction.** Long-press a daf → "Log with date / duration / note" → tap the bottom third of
*Mark learned*. `flutter test test/features/sheet_insets_test.dart`

### W3 · G2 — a profile with no backup does not get the all-clear

**Red, before.** `backup_tile_never_exported_test` — "Never exported" under a green tick reading
"Everything you have learned is in that backup". The title read `neverBackedUp`, the icon and
subtitle read `unsavedUnits == 0`, and nothing reconciled them; both-true is every profile on its
first day.

**Fix.** Three states — at risk, covered, and nothing to back up yet — with the green tick reserved
for a profile that really is covered. `BackupReminder` was right and is untouched: with no events,
zero unsaved units is the truth. The tile was drawing the wrong conclusion from it.

**Family.** A table over all four corners of exported × learned, because three of the four were
always right and a test for any one state would have passed. Mutation-checked: making `safe` ignore
`neverBackedUp` again fails exactly the new-profile row.

**Reproduction.** Create a second profile, open Settings → Backup.
`flutter test test/features/backup_reminder_test.dart`

### W4 · F5 — the restore preview folds each side under its own rules

F5 was flagged in the grade as reasoned-from-the-code and never reproduced. **It reproduces.**
Whether a unit counts as marked depends on the required-layer sets, and an import overwrites those
from the backup — so folding the backup's events against the *current* sets predicted the new log
under the old rules. A backup requiring the text alone, restored into a profile requiring text +
Rashi, promised "nothing will change" and then visibly re-marked two dapim.

**Fix.** Each side folds under the requirements that really apply to it: today's for today, and for
the outcome the sets the chosen mode leaves behind. `LayerRequirements.fromEntries` /
`OfferedLayers.fromEntries` exist because that transformation was written inline in both providers,
and a third copy for the preview is how a preview and an outcome drift apart.

**Watched fail.** Mutation: fold the restored side under the current requirements again → two of the
three new tests fail with 0 where they expect 2 and 1.

**Reproduction.** `flutter test test/features/restore_preview_test.dart`

### W5 · F4 — two restores ⚠️ ruled

`settingsRestoreFileSubtitle` promised "make this profile exactly match a backup, undoing anything
recorded since it" and only the log was reconciled.

**Ruling requested** (it changes what a destructive action destroys) **and given:** neither of the
grade's two options — keep today's narrow restore *and* add a wide one, as separate buttons.

**Fix.** `bool replace` becomes `ImportMode` (merge / restoreLog / restoreEverything). Settings gains
"Restore everything from file" beside "Restore learning from file", whose copy now says outright
that custom sefarim and settings are kept. The wide mode deletes the customisations the backup does
not contain and the confirmation counts them first — from the same method that performs the
deletion, because a preview computed separately from the outcome is one that will eventually
disagree with it. The red button now triggers on customisations too: a restore deleting three
sefarim and no units used to look harmless.

**The grader's probe was re-pointed, not deleted**, and now pins both halves — the wide mode deletes
the sefer, the narrow one keeps it, which is the promise its copy makes.

**Reproduction.** Make a custom sefer, export, make another, then run each restore.
`flutter test test/grader/restore_scope_test.dart test/features/restore_summary_test.dart`

### W6 · F3 — a repeating cycle is arithmetic, not 200,000 iterations

**Red, before.** `predictor_cost_test` — **47,890 ms** for one call in the test VM (~80 ms per
keystroke on the phone, AOT; the grade's own correction of its earlier ~3 s figure). The loop
allocated a `DateTime` per simulated day, inside `build()`, off the text field.

**Fix.** Whole cycles are one division; only the remainder — at most one cycle — is walked. The
horizon is checked before multiplying out, so a hopeless pace costs a division rather than 27 million
iterations. `finishDateWithShabbos` is deleted as an algorithm and expressed as the 7-day cycle it
always was.

**Family.** Three methods had three ideas of when "never" begins — 50,000 days, 200,000 days, and for
the flat form no horizon at all, so the dashboard would project the year 3027 for a pace the
calculator called hopeless. One `maxHorizonDays`, applied by all three, asserted.

**The test that matters is the equivalence, not the budget.** The old day-by-day walk is kept in the
test file as an independent implementation and the closed form is checked against it over nine cycle
shapes × every start offset × 40 remainders — including a cycle of `0.1`, where accumulating drifts
and one multiply does not.

**Also fixed:** the probe's own 16 ms budget around a single now-microsecond call was a coin flip on
a loaded machine — it failed inside a full parallel `flutter test` and passed alone, measuring the
scheduler. It times a thousand calls now.

**Reproduction.** Siyum calculator on Kol HaTorah Kula, type `0.05` into "amount per day".

### W7 · F2 — the Hebrew progress numbers

**Red, before.** `bidi_numerals_test`, and confirmed painted on two real screens: `0 / 929` rendered
as `929 / 0`. Digits are weak-LTR and a space-padded slash is neutral, so the bidi algorithm resolved
the neutrals from the paragraph and reversed the run — the operands *swap*, which reports a different
number.

**Fix.** A Unicode LTR isolate via `ltrNumerals`, not a `textDirection` override: the line must still
sit on the right in Hebrew and only its contents read left to right. Applied in every locale, since a
rule with a locale condition in it is a rule that gets tested in one locale. Applied to
`meforishCoverage` too, which is *safe as spelled* — "safe because of where its spaces are" is not a
property a string table should depend on.

**The probe could not have gone green as written**: it laid out a hard-coded `'5 / 100  (5%)'`, which
is a fact about Flutter, not about this app. Re-pointed at the shipped Hebrew table through the same
helper the widgets use, with its measurement and both cases intact, plus a control asserting the
un-isolated string really does reverse. `rtl_layout_test` gains the end-to-end half — the painted
tree row, measured — because a safe template and a widget that forgot to isolate it are
indistinguishable from the string's side. Mutation-checked (42.0 vs 196.0).

### W8 · G3 — the grid answers a keyboard ⚠️ ruled

Tab reached the cells and Enter marked one, so the grid looked keyboard-complete. Nothing showed
*which* cell was focused (the InkWell's highlight paints behind the filled container), and the cell
menu had no keyboard route at all — `lib/` contained no key handling of any kind.

**Ruled:** focus indicator *and* a keyboard route to the menu.

**Fix.** The cell draws its own focus ring, in the "on" colour of whichever background it sits on.
Shift+F10 and the context-menu key open the menu — both, because neither is universal. Four tests
drive the grid by keyboard alone, including that Enter still activates: a shortcut layer above an
InkWell is exactly the kind of thing that swallows activation. All four red on the previous commit.

**Not done, and named rather than left looking covered:** arrow keys do not move between cells, and
the settings list still ignores Page Down after a click — Flutter scrollables take keyboard scrolling
only when focused, and nothing here can make a click focus one without taking focus from what was
clicked.

### W9 · G4 — the app bar fits the app's name

The title read "Chovos …" on a 1220px phone, "Chovo…" at 1.6× font scale. Two halves, and the test
says both were needed: the title scales down instead of truncating, **and** Statistics and the Siyum
calculator move to the drawer, leaving the bar only what acts on the tree in front of you. Nothing is
removed — an unlabelled icon becomes a named row. Mutation-checked: with the actions moved but the
title left plain, both title tests still fail at 407 logical pixels.

### W10 · G7 — search shows every match

`.take(50)` with nothing to say it had happened. Deleted rather than replaced with a "50 of 312"
line: the catalog is ~312 nodes, the filter is one pass over a list already in memory, and results go
into a `ListView.builder`. The cap was buying nothing and costing correctness.

### W11 · G5 — a sefer's name is its name ⚠️ ruled

**Ruled:** strip the qualifier from the data and derive it.

241 parentheses (English and Hebrew) come out of the asset; `nodePath` derives the qualifier from the
node's ancestors. The root is never named — everything is under Kol HaTorah Kula.

**The family is bigger than the finding said, and the old integrity test is what named it:** search
results, the calculator's dropdown *and* both cycle pickers are flat lists with no tree around them,
propped up by those suffixes. All four are qualified now — the calculator especially, since a closed
dropdown shows one line with no indentation and no neighbours.

`catalog_integrity_test` loses "names are unique" and gains the property those lists actually need:
name **plus path** is unique, in both languages (0 clashes across 312 nodes), plus a check that no
name carries an ancestor as a suffix again. The Mishnayos "Taharos (Mesechta)" the grade flagged as
an inconsistency turns out not to be one: Mesechta Taharos really does sit inside Seder Taharos, and
the derived path says so.

### W12 · G6 — the language belongs to the device ⚠️ ruled

**Ruled:** language, theme and calendar go device-wide, seeded from the current profile.

The trap is specifically that the setting which hides the setting is the language: a Hebrew-only user
creating a profile for their son landed in an English, left-to-right settings screen and had to find
the toggle back without being able to read it.

`PrefKeys.deviceWide` names the three, `SettingsNotifier` decides in one place which store a key
lives in, and a second one-time migration moves them out of whichever profile the first one put them
in. Three consequences, each deliberate and each tested: they no longer ride in a backup, old backups
carrying them are skipped on import, and *Clear settings* — which resets one profile — leaves them
alone.

**Honest limitation:** the scoped copies under *other* profiles are never read again and cannot be
deleted, because `AppPreferences` has no way to enumerate keys. They sit inert.

`per_profile_settings_test` was rewritten rather than extended: it asserted the superseded rule.

## 3. Rulings taken

Four items changed what a user sees or owns, so each was put to the owner in plain words before
being built. All four answers are implemented as given; one differed from both options offered:

1. **Restore scope** → *"make two features — one that does what we do now and one that restores
   everything, two different buttons."* Built as `ImportMode` with two Settings actions.
2. **Catalog qualifier** → strip it from the data, compute it from the ancestor.
3. **Language / theme / calendar** → device-wide, seeded from the current profile.
4. **Desktop keyboard** → focus ring *and* a keyboard route to the cell menu.

## 4. What I did not verify

Reported in the negative, because a list of what was tested is not a measurement of what was not:

- **G2 on the device** — see §5. The other two hardware-found defects were re-measured on the
  phone that found them; this one was not.
- **The R8 mapping file is stale** (dated six days before this build) and the CI gate
  `test -f mapping.txt` cannot tell that. It is *correct* here — every change this round is Dart, so
  the Java/Kotlin inputs are unchanged and Gradle reused R8's output — but the gate would pass the
  same way if minification had genuinely stopped running. On a clean CI checkout the point is moot;
  as a local check it proves nothing.
- **The desktop file-write export branch** is still the one platform asymmetry nothing exercises —
  unchanged from the grade, and untouched by this work.
- **The v11 migration on a *large* database.** It ran on a real one, but that database held 35
  events. It rebuilds `learning_events` and copies every row; nobody has watched it do that to years
  of daf yomi.
- **Nothing was killed mid-migration.** The v11 step is guarded to be replay-safe the way its
  predecessors are, and the half-migrated fixture covers the old steps — but no test kills the
  process during the v11 rebuild specifically.
- **Hebrew wording of the four new strings.** Machine-complete and enforced, and the same caveat the
  README already carries applies to them.
- **iOS / macOS / Linux** — still never built by anyone.

**One defect found, which is what a phone is for.** `chovoshayom://sefer/shabbosShas`
opened the grid from cold and landed on **"Not found"** when the app was already
running — the same link, two answers, and the second is the common case because a
link is usually tapped by someone who has the app open. Android delivers a second
link through `onNewIntent`, which reaches the framework as `pushRouteInformation`,
and the framework's default handler rebuilds the route from path + query +
fragment — discarding the authority, where this app puts the screen *type*. The
"Not found" screen quoting `/shabbosShas` back is what named the cause.

Every deep-link test drove the cold path, and so did the hardware check that
signed deep links off in the 2026-07-30 grade. Fixed, three warm-channel tests
added and watched red, and re-verified on the device: cold opens the grid, warm
opens the grid, and a link we do not serve says so while quoting the whole URI.

**What the phone did not settle.** G2's fresh-profile corner was not driven: it
needs a new profile, and another app on this device (`com.vasikin.app`) foregrounds
itself every ~30 seconds, which ate several taps and one whole screenshot before I
noticed. Two consequences worth recording rather than hiding: one measurement was
taken against the wrong app's screen and discarded, and the `topResumedActivity`
check that distinguishes "my tap opened Recents" from "another app stole focus" is
the only reason the G1 result is trustworthy. The four-corner widget test is what
covers G2; the device is not.

Device state on the way out: daf 5 was marked and un-marked (net zero, though the
backup reminder now counts one *touched* unit, correctly by design), the language
was switched to Hebrew and back to English, and rotation was pinned to portrait.
